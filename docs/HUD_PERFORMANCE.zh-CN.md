# HUD 性能：刷新粒度与数据时效性

[英文 / English](HUD_PERFORMANCE.md) · [中文案例](README.zh-CN.md) · [可运行模型](../examples/hud-refresh/HudRefreshModel.lua) · [测试](../tests/test_hud_refresh.py)

**核心问题：队员列表虽然很小，但过于宽泛的刷新通知会触发一连串重复工作；减少这些工作，又不能让玩家看到过旧的信息。**

本节对应[战斗截图右侧的队员列表](../README.md#2-in-game-party-hud)，不是顶部的缩小匹配提示。它补充了我在这个 HUD 上的性能优化及后续维护经历。

## 背景：角色站着不动，为什么仍有不必要的 UI 工作？

一次 iOS 静止场景的性能问题指向原生组队管理器中的追踪玩家刷新逻辑。角色不动，并不意味着血量、距离和其他玩家都不会变化；但成员组成不变时，没有必要持续刷新列表结构。

需要分开考虑的是：**列表里有哪些人、这些人的实时状态是什么、较完整的玩家资料何时需要更新。** 三者不是同一种刷新需求。

## 定位：沿通知向下追踪，而不只看一个控件

相关链路为：

`UPzTeamManager::RefreshTraceLogic` → `RefreshTracePlayer` 事件 → `DungeonHUDTeamArea:RefreshTracePlayer` → 列表数据填充 → `DungeonHUDTeamItem:OnDataSet` → 玩家详情查询。

修改前，原生刷新路径每次 Tick 都无条件发出 Lua 事件。Lua 接收后清空列表条目，重新构造 RoleId 数据、获取数据桥接对象，再加入列表。条目绑定数据时，还会进入玩家详情请求链。

因此，成本不能只按“发了一次事件”或者“画了几个小控件”理解。ListView 的控件复用和数据对象池可以复用资源，但不能消除反复填充与绑定的工作。同样，调用详情接口也不等于立即产生一个独立网络请求，原有服务还有排队和请求合并机制。

这些调用关系可以解释优化目标，但不能代替原设备上的 profiler 记录或耗时数据。

## 第一层修改：减少成员结构的重复通知

我加入 `bTraceDirty`，在需要通知时才触发 `RefreshTracePlayer`，并在派发前清除标记。后续又把添加成员的标记位置收窄到“确实插入了新成员”的分支，避免反复确保同一个玩家在列表中时仍持续通知整个列表。

这是 **notification gating（通知门控）**，不是取消原生 Tick，也不是把所有 HUD 内容统一降频，更不是逐条 diff 的增量列表。真正发生成员刷新时，仍沿用原有清空并重新填充的路径。

原实现也有保守之处：移除路径只要对应的追踪原因分组存在，就可能设置 dirty，即使该玩家已经不在分组里。批量清理、全量同步也需要分别检查失效通知，不能把它描述为完善的全路径变更检测系统。

## 第二层修改：把支援按钮的变化与成员列表分开

附近玩法上下文变化时，支援入口可能需要出现或消失，但成员列表本身并没有变化。后续一次支援按钮显示错误的修复，先比较当前支援 ID 与保存的 ID，发生变化才发出 `RegionAssistIDUpdated`，Lua 单独刷新支援区域。

这样，仅支援上下文变化时，不必借助一次完整成员列表刷新来更新按钮。原来的成员列表刷新仍会顺带刷新支援区域；这是逐步收窄职责，而不是重写整套架构。这次修改原本由正确性问题触发，不应将它包装成单独测量过收益的性能项目。

## 第三层修改：缓存策略必须服从数据时效性

我的修改经历了三个阶段：

1. **最初的优化**：条目绑定时，详情查询从强制请求改为允许使用缓存。已有数据时可以减少详情刷新链的压力；没有缓存时仍可能需要请求。
2. **后续等级显示维护**：针对显示等级为 0 的问题，增加两秒一次的强制详情刷新，同时移除高频 brief 更新中对等级的赋值。血量、距离等仍走 brief 数据更新路径。
3. **进一步维护**：针对等级不一致的问题，绑定时又恢复强制详情查询，并增加一次立即显示刷新。因此，后期实现并不是“绑定时只读缓存”。

这是不同阶段的维护记录，不能据此断言所有后续等级问题都由最初的缓存修改造成。但它们能说明：优化之后，还要根据数据的实际含义和新鲜度要求修正策略。

最后并不是简单选择“全部缓存”或“全部每帧刷新”：**成员结构减少无意义通知；战斗中的变化信息保留独立更新；较完整的玩家资料重新获得明确的刷新机会。** 两秒只是发起请求的周期，不代表显示数据最多只会过旧两秒，因为还受服务延迟和失败影响。

## 贡献与取舍

这段工作体现的是：我减少了 C++、Lua、列表绑定之间不必要的重复刷新，并在玩家可见数据出现正确性问题后，调整了详情请求策略。

关键不是“调用越少越好”，而是区分 **unnecessary repetition（无意义重复）** 与 **necessary freshness（必要的数据更新）**。这是 UI 逻辑层的性能工作，不是引擎渲染优化；已有实现变化能够支持叙述，但不能据此声称提升了多少 FPS、减少了多少带宽。

## 这份 Portfolio 如何验证

[Lua 模型](../examples/hud-refresh/HudRefreshModel.lua)是为本案例独立编写的说明性代码，将通知、列表绑定和详情策略放在一个小例子里运行；它不是原生产代码，也不是原生管理器的替代实现。仓库已有的代码节选保持不变。

[测试](../tests/test_hud_refresh.py)覆盖稳定列表多次 Tick、批量添加、重复添加、移除及保守的无效移除通知、支援上下文独立更新、血量距离更新、过旧缓存、绑定时强制查询、周期详情刷新和缓存缺失。

计数只代表**模型中的事件、绑定和详情 API 调用次数**，不是 UMG 耗时、原生内存分配或实际网络流量。详情服务采用内存中的同步测试替身，不模拟真实异步回调、请求合并、失败处理或条目复用。具体范围见[测试说明](TESTING.md)。

## 如果现在重新验证，我会检查什么？

固定同一设备、场景和队伍人数，分别测试成员不变与频繁变动。分别统计原生到 Lua 的通知、列表重新填充、条目绑定、详情 API 调用和真正发出的服务请求，再结合游戏线程 UI 耗时及分配情况分析，不能直接把“少一次查询”换算成 FPS。

回归应覆盖加入／退出、区域切换、等级变化、缓存缺失、重新打开 HUD、批量清理、全量同步、延迟回包和条目复用，同时检查血量距离的响应性。以上是现在提出的验证方案，不是声称当时已经完整执行过。

进一步可以审计所有成员变更入口、明确各类数据的新鲜度要求，并考虑批量详情更新和生命周期安全的完成回调。这些是后续设计方向，不冒充已经交付的工作。

**表达关键词：** refresh granularity · redundant work · notification gating · list rebinding · cache policy · data freshness · correctness trade-off。
