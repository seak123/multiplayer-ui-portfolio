[英文首页](../README.md) · [完整案例](CASE_STUDY.md) · [架构](ARCHITECTURE.md) · [代码阅读路线](CODE_TOUR.md) · [问题定位](DEBUGGING.md)

## 工作范围与核心决策

我开发和维护了玩法及其配套 UI，包括组队／支援接入、缩小状态提示和后续问题修复，也独立完成了截图中的右侧队员 HUD。实现结合 C++ 游戏系统、Lua 界面逻辑和 UMG 控件，沿用团队共同维护的 UI 框架与多人服务。

案例围绕三个决策展开：**多个视图共用真实状态；复用玩家浏览能力但保留支援动作语义；沿完整请求与回调链解决 UI 问题。** 玩家由此能组队、邀请、准备、匹配，收起界面继续游戏，再恢复操作；需要帮助时则从玩法上下文进入支援列表。

## 案例 1：完整面板与缩小 HUD 的连续体验

**背景 / Context**

组队并不是只发生在一个静态菜单中。玩家可以在等队友、等准备或匹配时继续游戏，又要知道当前状态，并能快速回到操作入口。

**问题 / Challenge**

队长和队员的操作不同；准备、匹配和确认不是同一状态；关闭界面不等于离队。如果完整面板和 HUD 各自保存一套业务状态，就容易出现文字、按钮与实际队伍不一致。

**工作 / Actions**

我在现有 `TeamModel` 和组队服务上接入完整面板与缩小 HUD。模型读取真实队伍数据，结合角色、准备情况和匹配状态计算 `HUDState`；主面板和通知使用共同的状态来源。界面打开时重新读取当前数据，而不是只依靠之前收到的某一次事件。

隐藏／恢复属于展示行为；取消匹配、离队和解散属于明确的用户命令。HUD 恢复入口与退出确认分别处理。原实现并不是严格只显示一种视图：匹配中可以保留 HUD 和主面板同时存在。

**贡献 / Outcome**

把需要反复进入的多人流程接成连续体验：玩家可以收起界面继续游戏，保留状态和恢复入口。共同的状态派生也让主面板与缩小通知不一致时有明确的排查入口；各视图仍有专用呈现逻辑，需要一并验证。

**技术要点**：shared state · role-dependent controls · minimise and restore · player intent · live multiplayer state · presentation versus commands。

## 案例 2：复用多人浏览界面，但保留支援上下文

**背景 / Context**

玩家从世界中的玩法交互发起支援，需要找到合适的人、发送邀请，并看到等待／不可用的反馈。项目已经有多人浏览和玩家信息界面。

**问题 / Challenge**

直接复制一套列表会重复玩家信息、收藏、搜索和加载逻辑，但复用普通世界列表也不能忽略动作语义：此时玩家是在“邀请某人来支援这个活动”，不是普通访问世界。

**工作 / Actions**

原生交互携带 `AssistId` 发出事件，`MultiPlayerModel` 保留这个上下文，并以支援模式打开现有面板。父界面向列表传递 `bFromAssist`，列表选择支援推荐请求，条目切换到支援操作区。

点击后把 `OwnerRID` 与 `AssistId` 交给 C++ 管理器。管理器负责邀请等待／冷却数据并通知界面更新；每个条目根据自己的离线、忙碌和等待状态重新计算显示，不把“发出了请求”误认为“对方已接受”。

**设计取舍 / Trade-off**

复用了成熟的浏览能力，但代价是上下文条件分散在多层。如果未来继续增加很多动作类型，我会考虑小型的 action/context policy，避免不断累积布尔分支。这是现在的改进思考，不是已经交付过的重构。

**技术要点**：contextual support · reuse with an explicit action context · pending invitation · availability · shared browsing infrastructure · conditional complexity。

## 案例 3：支援搜索卡死——从完整回调链找原因

**背景 / Context**

支援界面搜索玩家时出现必现卡死。比起先怀疑某个控件画得太重，更有用的是追踪搜索结果进入条目后发生了哪些数据请求和回调。

**定位 / Reasoning**

旧代码中 `RefreshAssistGroup` 请求玩家详情；返回后触发 `OnAssistPlayerWatchCompleted`；有效的完成回调又进入刷新函数，再发起同一请求。

更隐蔽的是文件里存在两个同名的 Lua 方法定义，实际生效的是后一个。只看前面的方法、或者只删前面方法中的某段逻辑，并不能解释和修复真正执行的路径。

**修复 / Action**

修复删除了重复定义和重复请求路径，使完成回调只读取缓存并更新界面，而不继续请求同一份数据。等待状态与忙碌状态的显示逻辑仍然保留。

**验证 / Verification**

这次 Portfolio 新增了可控的 Lua 测试：假服务排队执行回调，旧代码在有界执行后仍然继续产生任务；修复后的版本处理一次回调就能清空队列。这里验证的是具体回调环，不是声称复现了原设备的完整性能情况。

**技术要点**：feedback loop · effective callback · duplicate method definition · request versus presentation refresh · bounded regression test · callback termination。

## 案例 4：一次邀请不应改变其他离线玩家的可用状态

另一个维护问题是点击在线玩家的邀请按钮后，其他离线玩家也出现了邀请按钮。原因不在按钮自身，而在共享刷新事件进入了只判断“是否已经邀请”的局部更新路径，遗漏了离线／忙碌等前提。

修复让正常玩家条目重新经过完整的 `RefreshAssistState`。关键在于**状态派生的入口必须完整且一致**，避免全局刷新事件让不同条目丢失各自的可用条件。

**技术要点**：complete state derivation · global event, per-item state · partial refresh · consistency。

## 共享 UI 框架与功能的连接

各层契约对应以下实际需求：

- **打开／关闭界面**：原生 Widget 生命周期连接 Lua Behaviour，按 unique ID 管理关联；界面销毁要清理事件和绑定。框架中的 scope 名称不等于隐藏时一定暂停所有订阅。
- **接入 UMG 与 Lua**：通过 `Elements`、子 `Behaviours`、事件与定时器配置建立契约；工程师实现交互与状态，UI 美术可以继续在既有编辑器里搭建控件、动画和反馈。
- **玩家列表**：Lua table 通过 `DataObjectPool` 进入原生 ListView；数据句柄复用与可视条目复用是两个问题，不应混称“对象池所以零开销”。
- **异步图片**：一个控件仍然存在，不代表旧图片请求仍适用于它。共享加载器用弱引用和当前期望路径校验，避免复用后应用旧结果；不能据此推断所有业务回调也都安全。
- **性能边界**：现有面板有周期详情刷新，HUD 有定时显示更新，因此不能说“所有内容完全由事件驱动”。搜索 debounce 属于共享浏览逻辑，它限制中间请求，但不保证响应顺序。
